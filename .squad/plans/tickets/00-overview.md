## Dependency notes

- **Story 05 depends on Story 01** (commit `8534be4`) for `lib/prisma.ts`, `auth.ts`, `app/providers.tsx` (the single `QueryClientProvider` + `SessionProvider`), `lib/roles.ts`, the `app/agent` / `app/portal` layouts, and the two nav components it adds one link to each. **On Story 02** (commit `fff097a`) for the `Customer` model, `requireAgent()`, the `lib/customers.ts` client-module idiom, and the `RouteContext<…>` / `PageProps<…>` + `await params` pattern. **On Story 03** (commit `ea52bab`) for `requireAdmin()`, `isStaff()`, `lib/api/http.ts`, and `lib/api/client.ts`'s `ApiError` / `request<T>()`.
- **Story 05 hard-depends on Story 04, which is implemented but not yet committed** at the time this plan was written (`app/(auth)/register/`, `app/api/register/`, `lib/registration.ts`, `lib/validation/email.ts`, `lib/validation/register.ts`, and `prisma/migrations/20260829011949_add_customer_user_link/` are untracked; `prisma/schema.prisma`, `prisma/seed.ts`, `middleware.ts` are modified). **Commit Story 04 first.** Customer-scoped ticket access is built entirely on `Customer.userId`; if that column is absent, the intake says to **flag it and stop**, never to fall back to an email match.
- **Shared contracts introduced by Story 05** — later stories consume these rather than redefining them:
  - `prisma/schema.prisma` → **`Ticket`** and **`Comment`**. `priority` and `status` are `String`, not Prisma enums, for the same reason `User.role` is: **SQLite has no `enum`**. The allowed values live in `lib/validation/ticket.ts` (`TICKET_PRIORITIES`, `TICKET_STATUSES`) and **must not** be re-listed anywhere else.
  - **`Ticket.assignedAgentId` is nullable, and `NULL` means "in the unassigned queue"** — a first-class workflow state, not a data gap. Any later feature that lists, counts, or reports on tickets must treat `NULL` as the queue, never as "missing".
  - **Referential actions are deliberate and asymmetric:** `Ticket.customer` is `Restrict` (a customer with tickets cannot be deleted), `Ticket.assignedAgent` is `SetNull` (deleting a staff account returns their tickets to the queue), `Comment.ticket` is `Cascade` (a deleted ticket takes its thread), `Comment.author` is `Restrict`. Do not relax any of these to `Cascade` for convenience.
  - `lib/ticket-access.ts` → **`resolveViewer()`**, the `Viewer` union (`staff` | `customer` | `orphan`), **`ticketScopeWhere()`**, and **`authorizeAssignmentChange()`**. The single implementation of both "which tickets may this caller see" and "may this caller change `assignedAgentId` from X to Y". `authorizeAssignmentChange` is a **pure function** — no Prisma, no `Request` — so the whole truth table is testable. A second copy of either rule is a security bug.
  - **The customer scope goes inside the Prisma `where`**, via `findFirst({ where: { id, ...ticketScopeWhere(viewer) } })` — never `findUnique` followed by an ownership `if`. A customer asking for someone else's ticket id gets the same response a nonexistent id gets: **no existence oracle**.
  - `lib/sla.ts` → **`isSlaBreached()`**, `isSlaHalfElapsed()`, `defaultDueAt()`, `SLA_HOURS`. Pure, with **no server-only imports**, because both route handlers and client components import it. **There is no `slaBreached` column**; every read path computes it server-side and ships the boolean in the payload. Clients render the flag they receive — recomputing in the browser makes the SLA depend on the viewer's clock.
  - **`SLA_HOURS` (HIGH 4 / MEDIUM 24 / LOW 72) is a product decision made in Story 05, not a fixed acceptance criterion.** The criteria only required `dueAt` to be nullable and the sweep to act on a half-elapsed window, which is unreachable if `dueAt` is always `NULL`. Change the table freely; do not move it into the database.
  - `lib/validation/ticket.ts` → `createTicketSchema` (agent, has `customerId` + `assignToMe`) and **`createPortalTicketSchema`** (customer, has neither). The split is the mechanism that stops a customer setting the owning customer or an assignee from a request body. Do not merge them.
  - `lib/tickets.ts` → `ticketKeys`, the fetch/mutate wrappers, and the `TicketListItem` / `TicketDetail` / `TicketComment` types. `ticketKeys.comments(id)` **nests under** `ticketKeys.detail(id)` on purpose, so invalidating the detail also refreshes the thread.
  - `components/agent/tickets/comment-thread.tsx` → shared by the agent **and** portal detail pages. There must never be a portal-specific copy.
- **Behaviour introduced by Story 05** — later stories must assume these semantics:
  - **`/api/tickets` is one endpoint serving both audiences.** The portal calls the same `GET` as the agent area; the server scopes the result. Do not add a parallel `/api/portal/tickets`.
  - **A `CLOSED` ticket's status is frozen on `PATCH`** (`409`). `POST /api/tickets/[id]/reopen` is the only path back to `OPEN`, and it takes no body.
  - **`DELETE /api/tickets/[id]` is `requireAdmin()`, not `requireAgent()`** — it destroys the comment thread with it.
  - **`/api/tickets/assign-sweep` is a static segment sitting next to `/api/tickets/[id]`.** Next.js resolves static before dynamic, so it is reached correctly; the `curl` in Test Plan item 9 is what proves it has not regressed.
  - **The comment thread is polling, not push** — an 8 s `refetchInterval`, `refetchIntervalInBackground` left at its default `false`. This is the repo's **first** polling query; there were zero `refetchInterval` hits before this story.
  - `components/ui/select.tsx` and `components/ui/badge.tsx` are added via `npx shadcn@latest add select badge --base radix --preset nova`, matching `components.json`'s `"style": "radix-nova"`. They must import from the unified `radix-ui` package, as `components/ui/button.tsx:3` does — a generated `@radix-ui/react-select` import means an unpinned dependency slipped in.
- **One migration.** `prisma/migrations/<timestamp>_add_ticket_and_comment/` — two plain `CreateTable`s plus four `CreateIndex`es. **`Customer` and `User` gain no columns**; if the diff shows a `new_Customer` table redefinition, the schema edit was wrong.
- **Deferred out of Story 05:**
  - **A real scheduled/background assignment job.** The sweep is a manual admin action, recorded as such in a doc comment on the route. A cron or queue worker is the follow-up.
  - **Real-time push for the comment thread.** WebSockets are explicitly out of scope; polling is the shipped answer.
  - **Optimistic-locking on claim.** Two agents claiming simultaneously is a last-write-wins race with no data corruption. `updateMany({ where: { id, assignedAgentId: null } })` plus a `count === 0` check is the fix if it ever matters.
  - **Notifications and alerts, audit logging of assignment/status changes, and CSAT** — each named in the intake as a separate story.
  - **Email / WhatsApp / SMS delivery, AI-suggested replies, auto-categorisation.** `Ticket.category` is deliberately free text so a later categorisation story is not fighting a fixed list.
  - **Ticket attachments, per-customer SLA policies, and a saved-view / bulk-action layer.** Not in the acceptance criteria.
- **Still no automated test framework.** Stories 01–04 all deferred it and Story 05's intake does not ask for one either, so this ships a manual + `curl` test plan. `authorizeAssignmentChange` and the three `lib/sla.ts` helpers were written as pure functions specifically so Test Plan items 4–13 become unit tests the day a runner lands — that is the highest-value first test suite in this repo.
